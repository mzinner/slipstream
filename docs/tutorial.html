Part I · The model

1 · The model: Qwen3.8-Flash-Next

Before the engine, the machine it runs on: a Mixture-of-Experts hybrid-attention model whose upstream architecture name is qwen4exp. Every number in this section is from the published config.json, mirrored as compile-time constants in models/qwen4exp/Qwen4Exp.hpp and checked against the package by the loader.

48layers: 36 GDN + 12 sparse attention (1 in 4)
512 → 10experts per layer; only 10 fire per token
~100 GBweights — too big for this 64 GB Mac
+1MTP draft head: the model ships its own guesser

1.1 The blocks in one layer

BlockWhat it isWhere it runs in this repo
GDN mixer (36 of 48 layers) Gated DeltaNet linear attention: a recurrent state per request, constant cost per token, no KV growth runtime/ops/GDN.cpp · state in runtime/model/QwenState.*
Sparse attention (every 4th layer) Full attention with a learned indexer (4 heads, 1 KV head, head dim 128) that picks which KV pages to read sparse picker kernel in models/qwen4exp/kernels/

Why the architecture looks exotic: every unusual block is a bet on the same problem — decode is memory-bandwidth bound. GDN shrinks the state, the indexer shrinks the KV reads, MoE shrinks the compute per token, and the MTP head turns one weight read into several accepted tokens. The one place the bet is extreme is the MoE: see below.

Sections 1.1–1.8 below are integrated from the standalone first-principles tutorial “Why Flash-Next Fits in 64 GB” (~/Documents/shared-with-google-drive/ml-study/flashnext-tutorial/), whose numeric self-checks live in its spec.json; every figure here was re-verified against it and against the engine's layout constants in models/qwen4exp/Qwen4Exp.hpp. The original keeps its figures (SVG); this version carries the derivations in text.

1.1 The one inequality: speed is bytes, not math

Two ideas are all you need. A transformer layer is a pile of matrix multiplications; and at batch size 1 a token's speed is set by how many bytes must be read to produce it, not by how many multiplications are done — each weight is used for one multiply-accumulate and then discarded. So for a dense model that must read all of its B bytes per token, on a machine that moves R bytes/s: 

(1.1)   tokens/s  ≤  R / B
(1.2)   sparse ÷ dense  =  B_dense / B_sparse          (R cancels — count bytes, not FLOPs)

The puzzle: Qwen3.8-Flash-Next holds 176.94 billion parameters, 93.82 GiB on disk, yet decodes 26.5 tok/s on a 64 GB machine (llama.cpp baseline; 41 tok/s in Slipstream). It is not compression. The model reads only a slice of itself per token: 

(1.3)   always-on trunk (attention, norms, routers, head)  =  3.4 GiB
        experts this token uses (§1.3)                     =  1.2359 GiB
        bytes read per token                               =  4.6359 GiB
(1.4)   93.82 / 4.6359 = 20.24×   → dense ceiling 1.31 tok/s × 20.24 = 26.5 tok/s measured

One twentieth of the file crosses the memory bus per token; the measured 26.5 tok/s implies ≈131.9 GB/s of weight traffic — derived from the model, not assumed. Every design choice in the rest of this section is an answer to equation (1.1): make the bytes-read-per-token small, and keep them small as the model grows and as the context grows.

1.2 The MoE block, end to end, by hand

The running example is Tiny-Next: 4 dimensions, 4 experts, top-2, input x = (1, 0, 2, −1) — Flash-Next shrunk ~100×, behaving identically.

Route. A router matrix has one row per expert; each row scores its expert's relevance to this token by dot product:

r0·x = 1    r1·x = 4    r2·x = 1    r3·x = 3        → keep the top 2: experts 1 and 3

Experts 0 and 2 are not multiplied by zero — their weights are never fetched. That sentence is the whole tutorial in five words. Softmax is taken over the winners only (over all four, the losers would steal probability mass from a blend that never uses them): 

(2.3)   g1 = e⁴/(e⁴+e³) = 0.7311        g3 = e³/(e⁴+e³) = 0.2689

Run the winners. Each expert is a SwiGLU MLP — up-projection U, gate G, down-projection D — computing D(SiLU(Gx) ⊙ Ux), SiLU(z) = z/(1+e⁻ᶻ): 

expert 1:  U₁x = (3,−1)   G₁x = (2,0)   →  h₁ = (SiLU(2)·3, SiLU(0)·(−1)) = (5.2848, 0)
         gate SiLU(0)=0 switched that hidden unit off entirely — that is what a gate is
expert 3:  U₃x = (−1,1)   G₃x = (1,2)   →  h₃ = (−0.7311, 1.7616)
blend:     y = 0.7311·D₁h₁ + 0.2689·D₃h₃ = (4.1408, 0.4737, 3.8637, −0.1966)   ✓ spec.json

Nothing in the derivation cared about the number 4. With E = 512 experts per layer and k = 10 active (plus 1 shared expert that always runs — the DeepSeek-MoE refinement): 

(2.10)  k/E = 10/512 = 1.9531%   →  a token visits 10×48 = 480 of the 512×48 = 24,576 experts.
        the model has the capacity of 24,576 experts and the running cost of 480.

1.3 The arithmetic that lets weights live on disk

(3.1)  one expert  = 3 matrices × (2560×640) × 0.5625 B (4.5-bit avg) = 2.6367 MiB
(3.2)  per token   = 10 experts × 48 layers × 2.6367 MiB             = 1.2359 GiB
(3.3)  demand      = 1.2359 GiB × 26.5 tok/s                         = 35.16 GB/s   ← from SSD?
(3.4)  misses only = 35.16 × (1 − 0.9931)                            = 0.2426 GB/s
(3.5)  headroom    = 9.87 / 0.2426                                   = 40.7×

The SSD here does 9.87 GB/s (measured, page cache bypassed), so the answer to (3.3) must be no — and it is, because routing follows the text and the text changes slowly: a cache of recently used experts hits 99.31% of lookups once warm. ~32 GiB of experts sit in RAM (257 of 512 slots per layer as measured; Slipstream today caches 272 per layer in 34 GiB with a per-layer fitted profile, §5.1), the remaining ~32 GiB sit on the SSD, and the model cannot tell. The same locality argument covers the 26.8 GiB n-gram table (§1.8): its rows are 90 bytes, so a token touches a handful of kilobytes of it.

What breaks this: if routing were uniform-random, the hit rate would collapse toward 257/512 = 50%, the disk would be asked for 17.6 GB/s, and the design dies. Streaming depends on routing predictability — an empirical property of the trained model, not a runtime guarantee. The engine's read-ahead (§5.1) bets on it too: it fetches 6 predicted experts per row while the GPU computes, right ~2/3 of the time.

1.4 Sparse attention: paying 2% to avoid 98%

Sparsity fixed the weights; context is the other thing that grows. Attention compares each new token against all n predecessors: with H = 24 heads of d_h = 256 (12 attention layers), at n = 131,072: 

(4.2)  full:        131,072 × 24 × 256            = 805,306,368 MACs / layer / token
(4.3)  indexer:     (131,072/4) × 4 × 128         =  16,777,216   = 2.0833% of full
(4.4)  on selected:     2,048 × 24 × 256          =  12,582,912
(4.5)  805,306,368 / (16,777,216 + 12,582,912)    =        27.43× cheaper

The indexer is a miniature attention — 4 heads of 128 against 24 of 256 — whose only job is to score the context so the real attention runs on the top slice. Two refinements make it cheap: it scores the context compressed 4:1 (blocks of 4 tokens), and it selects whole blocks (the budget is 2,048 tokens in blocks anyway). The indexer can pick badly — then the layer is confidently blind to a relevant passage — but the asymmetry favors it: a miss costs accuracy on one token, full attention costs 27× on every token, and the model is trained with the indexer in place to make its picks survivable. Break-even is ~2,091 tokens, which is why the engine runs plain attention below the budget; the reference-check prompt in ~/models/qwen38-flash-next-reference/ deliberately crosses 2,048 to catch indexer bugs (models/qwen4exp/tools/checks/check_indexer.py).

Only these 12 layers store KV at all: 12 layers × 2 KV heads × (256+256) × 2 B = 24 KiB/token = 3.0 GiB at 131k (eq. 4.6) — small enough to keep resident, which is why no cache streaming is needed here, only the paged 8-bit KV cache (§6).

1.5 Three cheap layers for every expensive one (GDN)

Does every layer need to be attention? A fixed-size summary S carried forward, updated per token, costs the same at token 1,000,000 as at token 10 — but compresses, so old detail decays. Attention has unbounded cost and perfect recall; the recurrent summary has bounded cost and lossy recall. Flash-Next hedges 3:1 — 36 gated DeltaNet layers per 12 attention layers — and the delta rule is what makes the cheap one usable: 

(5.1)   S_t = f(S_{t−1}, x_t)                        cost independent of t
(5.2)   S_t = α_t ⊙ S_{t−1} + β_t ⊙ Δ_t              α decides what to KEEP,
                                                      Δ is a delta — nudge, not replace

Both α and β are computed from the current token: the layer learns when to remember. The state is 48 value heads × 128 dimensions (16 key heads, 16:3 is the GQA of linear attention), plus a short convolution (dim 10,240) — all in the engine's per-request recurrent state (runtime/model/QwenState.*, runtime/ops/GDN.cpp). Measured effect: decode falls only 21.0 → 17.7 tok/s from context 0 to 65k on the llama.cpp baseline (−16%); a pure-attention model of this size falls far steeper. The interleave also explains a quantization choice: GDN state stays F32 while experts sit at 4.5 bits — by (5.2), an error in a recurrent state compounds across the whole sequence, while an error in a feed-forward weight affects one token.

1.6 Four rivers instead of one (hyper-connections)

The residual stream z ← z + sublayer(z) has one structural weakness: all 96 sublayers read and write the same 2,560-wide channel, and distant sublayers interfere. The narrowest fix is more channels: Flash-Next carries m = 4 streams (working state 4×2560 = 10,240 wide). A sublayer expects 2,560 inputs, so naively you'd read one stream (four non-communicating stacks) or concatenate (4× cost — exactly the cost this whole model exists to avoid). The answer is a learned low-rank mixture:

(6.2)   u  = mix(z₁..z₄)            rank-320 gate collapses 4 streams → 2,560, pre-sublayer
        zᵢ ← zᵢ + wᵢ · sublayer(u)   learned inject writes the result back across all 4

This wraps every mixer and every MLP: twice per block, 96 times. The sublayer never knows there are four streams, so the cost is the mixing only — ~30% of decode, kept affordable because the mix is rank 320, not full rank (checkpoint tensors hc_attn_*, hc_ffn_*; engine kernels hyper_connection*.metal, mix weights deliberately 8-bit). Whether four streams are worth 30% is an empirical training-time choice; what the derivation establishes is the shape of the trade.

1.7 Getting tokens for free (the MTP head)

One more attack on equation (1.1): produce more than one token per weight-read. Suppose a cheap oracle knew the next two tokens — you'd feed all three positions through and verify, and verification is nearly free because the expensive part (fetching the weights) is shared. The model ships the oracle: a small draft layer (trunk attention shape, fed the trunk's state captured from layer 43, ~2.4 GiB against 93.82) guesses ahead; the trunk checks in one pass. With acceptance probability a and draft depth 2: 

(7.1)   E[tokens per pass] = 1 + a + a²     (the 1 is the trunk's own token, always kept;
                                            a guess after a rejected guess is discarded)
(7.2)   measured a = 0.647  →  1 + 0.647 + 0.647² = 2.0645 tokens/pass
        measured speedup 26.5/18.04 = 1.469×  (the head is extra work; 7.1 is a ceiling)

Deeper drafts are not better: acceptance falls with depth (measured a = 0.647 / 0.525 / 0.429 at depths 2/3/4) while drafting cost rises linearly — speed peaked at 26.85 / 25.63 / 23.06 tok/s, optimum depth 2 on this checkpoint (another checkpoint peaked at 3: the optimum follows the acceptance curve, not the architecture). Slipstream rides the same curve with a confidence stop (§5). The trap that caught its builders: the draft head must be fed the model's 4-stream state from §1.6, not the collapsed 2,560 vector. Nothing errors — acceptance silently falls to ~1%, and the tell is an acceptance rate that doesn't move when the draft weights change.

1.8 The block no derivation predicted: the n-gram embedding

Layer 1 adds a per-layer embedding the derivations above don't need: hashes of the last 3 tokens (order 3, 8 heads per order, each head its own prime-sized vocabulary from base 20,000,000) look up rows in a table of 320,001,536 × 2560 at Q4 ≈ 26.8 GiB, fed through a dilated convolution (4 taps). It buys learned token-identity features at lookup cost — cheap exactly because a token touches a handful of 90-byte rows (locality again, §1.3). On disk it is the third biggest object in the package; in compute it is a rounding error. Engine: ngram_embedding*.metal, layout constants in Qwen4Exp.hpp:80-95. The port notes one trap it set: 16 heads × 160 and 8 heads × 2560 have the same element count — check shapes, never byte totals.

No single one makes a 176.94-billion-parameter model run on a 64 GB laptop — the product of all of them does. Problems (from the standalone tutorial; answers collapsed)
  1. ★ With eq. (1.1) only: show the dense 93.82 GiB model caps at 1.31 tok/s at 131.9 GB/s, and 4.6359 GiB/token gives 26.5.
    Answer93.82 GiB × 1.0737 = 100.74 GB; 131.9/100.74 = 1.31. 4.6359 GiB = 4.978 GB; 131.9/4.978 = 26.5. Equivalently 1.31 × 20.24 = 26.5.
  2. Recompute the eq. (2.3) blend with router scores (1, 4, 1, 4). Which experts, which weights, and why is “which experts” now ambiguous?
    AnswerTie between experts 1 and 3 (both 4); softmax over winners is now (0.5, 0.5) if both are kept — the selection rule must break ties, and the router gives no preference. Any tie-break is a silent numerical choice.
  3. Raising the expert cache 257 → 400 slots/layer lifts the hit rate 99.31% → 99.8%. Eq. (3.4): new disk traffic?
    Answer35.16 × (1 − 0.998) = 0.0703 GB/s, vs 0.2426. The disk was already at 2.5% of its ability (40.7× headroom) — you would buy a 5th× headroom with 18 GiB of the scarcest resource. Not worth it; spend RAM on the KV cache instead.
  4. ★ Indexer break-even: at what n does scoring n/4 blocks + attending 2,048 exceed full attention?
    Answer(n/4)(4)(128) + 2048·24·256 ≥ n·24·256 → 128n + 12,582,912 ≥ 6144n → n ≤ 12,582,912/6016 ≈ 2,091. Below that the indexer costs more than it saves.
  5. Using eq. (5.2), why does state error compound while feed-forward weight error does not? What property of αₜ bounds the compounding?
    AnswerS_t feeds S_{t+1}: any perturbation is multiplied by α's all the way forward. Feed-forward error touches one token's one activation. If αₜ ≤ α* < 1 with margin (the gate genuinely forgets), perturbations decay geometrically — bounded compounding.
  6. Eq. (7.1) at depths 2/3/4 with measured a = 0.647/0.525/0.429. Why does the ceiling barely move?
    Answer1+a+a² = 2.064; 1+a+a²+a³ = 2.271; depth-4 sum = 2.226 (a falls faster than the sum grows — the 4th term adds 0.429³ = 0.079 and the 4th draft costs a full drafting unit).
  7. Eq. (4.6) with 24 KV heads instead of 2: new KV size, and what does it do to §1.3's “cache stays resident”?
    Answer24/2 × 24 KiB = 288 KiB/token → 36 GiB at 131k: KV alone eats the expert cache. GQA (2 KV heads) is what makes resident KV affordable.
  8. Does the Q8_0 shared expert fit the “bits where errors change decisions” rule?
    AnswerPartially: it runs on every token (use ≈ every token, so bits are cheap per use) and its output is added to every routed expert's, nudging the final distribution on every token — closer to the “decision” rule than the routed experts, whose blend weights gate their influence.
  9. Double the experts to 1,024 with 10 active: capacity, bytes/token, file size, hit rate — which decides if it's a good idea on 64 GB?
    AnswerCapacity ↑ (more experts of the same size); bytes/token unchanged (10 are read either way); file doubles to ~155 GiB; hit rate falls — 272 cached slots now cover 272/1024 not 272/512 per layer, so misses rise toward the SSD's limit. The hit rate decides — and it likely loses the machine.

Part II · Getting small: Swift and the engine line

2 · Swift quantization, and how the engines evolved

Swift-Qwen3.8 is the name of this model family's local quantized builds — ~/models/swift-qwen38-flash-next-v3/, swift-qwen38-27b/, and their *-splash packages. "Getting Swift" is the quantization work; the engine line is what ran it. Both lines are history that explains why Slipstream looks the way it does.

2.1 The quantization recipe

Experts are 97% of the weights and are touched 10-at-a-time, so they tolerate small quantizers; everything that runs on every token stays wide. That asymmetry is the whole recipe:

2.2 The engine line: llama.cpp fork → Splash → Slipstream

EngineWhat it addedDecode

Quality held through every step: greedy output is token-identical to Splash, and against the bf16 reference Slipstream picks the same top token 91% of the time (llama.cpp V3: 89%). Quality is proven with a fixed method — reference logits, top-pick agreement, KL, and the greedy 10-prompt regression suite — all of it in docs/new-model-playbook.md.

The two facts that define the project: (1) quantization made the model small enough to exist on this Mac; (2) the model's own MTP head turns every expensive expert read into ~3 accepted tokens. Slipstream is the engine that exploits both.

How to read this tutorial

Pointers look like runtime/ops/Linear.cpp or models/qwen4exp/kernels/mtp_pick.metal:15 — a file path, optionally with a line number. They are relative to the repository root. Open each file as you go; snippets are copied from the code (long bodies are summarized; line numbers point at the originals).

One sentence to keep in mind: a Python server turns chat requests into tokens and pipes them to one native engine process; the engine schedules; a shared runtime runs the decode loop; and everything specific to one model lives in one folder, models/qwen4exp/.

Part III · The Slipstream framework

3 · The big picture: seven layers

The system is a stack. Requests flow down; each layer owns a narrow job and knows nothing about layers above it. The diagram below is the entire architecture — everything else in this tutorial zooms into one of these boxes.

That is why adding a model means adding a folder, not patching the engine.

5 · One decode step

This is the heart of the speed. Instead of the full model producing one token at a time, a small draft head built into the model guesses the next few tokens first, and the full model checks all of them in a single pass.

Figure 3 — One decode step. Draft ~7 ms, verify ~65 ms; both numbers from docs/architecture.md.

Why this is safe: the draft head is an extra layer inside the checkpoint (the MTP head). The full model verifies every guess, so the output is token-for-token identical to running the full model alone — the draft only changes speed, never the answer.

Open models/qwen4exp/Qwen4ExpTarget.cpp:2493 to see the real dispatch that launches the draft head's pick kernel — it is the running example of section 7.

5.1 · The pipelined step: SSD reads under the GPU

A step touches ~100 GB of weights; 34 GiB sit in RAM and the rest lives on SSD. The naive loop is serial — for each layer: find the missing experts, read them, run them, repeat — and the GPU idles through every read. Pipelined decode removes the serialization by encoding the whole step as one multi-stage submission before it starts (models/qwen4exp/Qwen4ExpTarget.cpp:2755-2910):

  • The resident prefix goes first. The embedding and the current layer's path up to its router are encoded into one graph and submitted immediately (:2759-2769). There is deliberately no read-ahead of the previous step's experts: “after a long prompt that is nearly every expert, ~68 GB the OS then reads in the background for minutes, stalling decode” (:2770-2772). Misses are fetched on demand.
  • Every remaining layer becomes stages of one pipeline. All the layer dispatches are appended to one list with a stage boundary at each router (:2798-2800), and the whole list leaves in a single submitPipelineAsync call (:2869-2871): one command buffer per stage, all committed at once. The GPU runs each stage the moment the host releases it — the GPU never waits for a submission, only for a host signal (section 6.2).
  • Between stages, the host reads. The host loop (:2876-2905) waits for the event “layer L−1's compute is done”, reads that router's scores out of GPU memory, picks the 10 experts per row (hostSelect), stages the experts already cached, releases their stage, reads the missing experts from SSD into cache slots, then releases the rest of the layer.

With waves (on by default; SPLASH_DECODE_WAVES=0 turns it off) every layer after the first is two stages, straight from the code comment (:2804-2810): 

// Waves: every layer after the first is two stages. A runs the experts
// already cached while the host reads the missing ones; B runs those,
// then the rest of the layer as before. A is quiet (raises no event), so
// the host starts B as soon as its reads land. Same outputs; 84.6 -> 79.6
// ms a step on the 10-prompt suite. SPLASH_DECODE_WAVES=0 turns it off.

Lookahead shrinks the reads themselves: stage L also encodes the router scores for layer L+2, so the host can prefetch that layer's experts early — but only the predicted top 6 of each row's 10, a number measured, not guessed (:2081-2086): 

// The predicted top 6 of each row's 10. The prediction is right for
// ~2/3 of its top 10, and every wrong guess is a wasted SSD read that
// competes with the reads that matter: 10 -> 6 cut reads 133 -> 95 a
// step and gave 38.6 -> 40.3 tok/s on the 10-prompt suite (5-8 tie;
// 12 and none are slower). SPLASH_LOOKAHEAD_EXPERTS overrides.

The reads themselves are plain preads — one per expert matrix, all in flight on a GCD queue: “The SSD reaches ~15 GB/s this way; faulting pages in one at a time reached ~1.5”, and splitting each read into four smaller in-flight reads measured slower (staging 30 → 39 ms a step) — readMissedExperts, Qwen4ExpTarget.cpp:385-400.

6 · The GPU runtime: what a dispatch becomes

Section 5 shows the call that launches a kernel. This section is what receives it — runtime/metal/MetalBackend.mm — and the three pieces of machinery the pipelined step of section 5.1 leans on: a lazy pipeline cache, an event counter shared between GPU and host, and a residency set.

6.1 · Submit: validate, resolve, chunk, commit

submitCommand is thin — submitCommandAsync(dispatches).wait() (MetalBackend.mm:1216-1219). The async path, before it commits anything (:1342-1520):

  • Validates every dispatch: no empty buffers, no duplicate binding indices, threads-per-threadgroup within the pipeline's own limit (:1385-1421). A typo in a binding index is an exception, not a silent garbage kernel.
  • Resolves pipelines lazily. The metallib is loaded once at startup (section 7.7); a kernel's compiled pipeline is created on its first use and cached by name (MetalBackend.mm:500-525):
id<MTLComputePipelineState> cached = [pipelines objectForKey:key];
if (cached) return cached;
id<MTLFunction> function = [library newFunctionWithName:key];
if (!function)
    throw MetalBackendError("missing Metal function: " + std::string(name));
... newComputePipelineStateWithFunction ...
[pipelines setObject:result forKey:key];

So a misspelled kernel name throws at the first dispatch that uses it — with the name in the message — not at load time.

  • Chunks by working set. A long dispatch list is split into command buffers whose buffers total at most max(4 GiB, recommendedMaxWorkingSetBytes / 2) (:1447-1452, overridable with SPLASH_CHUNK_WORKING_SET_GIB). A prefill that touches tens of GB of weights becomes many commits the GPU drains continuously, instead of one commit the driver must fit.

Every submission returns a CommandTicket, and a watchdog catches a command that never comes back: default 120 s, and “A completed GPU command stops this clock even if its model ticket continues waiting for CPU work” (runtime/metal/CommandWatchdog.hpp:10-13).

6.2 · Pipeline events: a counter the GPU and host take turns raising

The whole protocol is the doc comment on the API (runtime/metal/MetalBackend.hpp:346-352): 

// A pipeline: the dispatches split into stages at `stageStarts`, one
// command buffer each, committed together. Stage k > 0 waits for the
// pipeline event to reach base + 2k and raises it to base + 2k + 1 when it
// completes (stage 0 raises base + 1). The caller does host work between
// stages: waitPipelineEvent(base + 2k - 1), then signalPipelineEvent(base +
// 2k). The GPU never waits for a submission, only for that signal.

It is one monotonic 64-bit MTLSharedEvent counter shared by all pipelines (reservePipelineEvents hands out a fresh base and advances it by 2·stages + 2, MetalBackend.mm:1260-1270), so an event value can never be reused while a previous step is still in flight. The host waits are poll-first, with the reason measured (MetalBackend.mm:1272-1275): 

// Poll first: a pipeline hands off once per layer, and a blocking wait's
// wake-up latency, paid 47 times a token, cost ~9 ms. Spinning costs one
// core for the few hundred microseconds a stage takes.

One refinement makes waves possible: a quiet stage waits for its event (base + 2k) but raises nothing when it ends (MetalBackend.hpp:362-365) — “the host can then start stage k + 1 without waiting for stage k: the event only ever moves forward”. That is wave A of section 5.1: the cached-expert stage runs, the host's reads land, the host raises the next value, wave B starts — the quiet stage's completion is never on the critical path.

Figure 5 — The pipeline-event protocol. Odd values: a GPU stage finished. Even values: the host released the next stage. Quiet stages take part without raising, so the host controls release.

6.3 · Residency: pinning the expert cache

Metal maps buffers into the GPU's page tables lazily. For a normal app that is a feature; for a 34 GiB expert cache touched every layer it is a stall, as the call site spells out (models/qwen4exp/Qwen4Exp.cpp:727-730): 

// Keep every expert cache resident on the GPU. Otherwise the driver maps
// each layer's cache on first use - ~14 ms a layer, ~0.7 s for a step -
// and again after a long prompt, streamed through whole layer files,
// evicted them.

backend.keepResident(resident) (Qwen4Exp.cpp:742) puts the cache buffers in a residency set attached to the queue; the backend adds each allocation and calls requestResidency once (MetalBackend.mm:1240-1258) — “instead of the driver making them resident when a command first uses them — and again after something large evicted them” (MetalBackend.hpp:353-356). The host-side staging buffers for streamed experts are additionally mlocked (Qwen4Exp.cpp:738-740) so the pages the SSD reads land where the GPU is already looking. SPLASH_NO_RESIDENCY_SET=1 disables it for A/B measurement.

7.3 · Stage 3 first: what a kernel actually looks like

Start with the simplest real kernel in the repo — RMS normalization, runtime/metal/kernels/shared/normalization.metal (20 lines, the whole file): 

kernel void norm_rms(device const bfloat *input  [[buffer(0)]],
                     device const bfloat *weight [[buffer(1)]],
                     device bfloat *output       [[buffer(2)]],
                     constant uint &width       [[buffer(3)]],
                     uint row         [[threadgroup_position_in_grid]],
                     uint thread_index [[thread_index_in_threadgroup]],
                     uint lane        [[thread_index_in_simdgroup]],
                     uint simd_group  [[simdgroup_index_in_threadgroup]]) {
  threadgroup float reductions[8];
  float inverse_rms = rms_inverse(input + row * width, width, reductions,
                                  thread_index, lane, simd_group);
  for (uint column = thread_index; column < width; column += 256) {
    output[row * width + column] =
        bfloat(float(input[row * width + column]) * inverse_rms *
               float(weight[column]));
  }
}

Read it top to bottom — every line is a pattern you will reuse:

LineWhat it means
kernel void norm_rms(...) A GPU function. Its name is the dispatch name used later by C++.
device const bfloat *input [[buffer(0)]] A pointer into GPU memory, bound at index 0. The C++ side passes buffers in a list; buffer i in the list is [[buffer(i)]] here.
constant uint &width [[buffer(3)]] A small scalar parameter, bound after the device buffers.
uint row [[threadgroup_position_in_grid]] "Which piece of the work am I?" Here: one threadgroup per row, so threadgroup X normalizes row X.
uint thread_index (0…255) Which of the 256 threads inside my threadgroup am I.
lane / simd_group My position inside a 32-lane SIMD group — used by the fast 32-wide reductions.
threadgroup float reductions[8] Scratch memory shared by the 256 threads of this threadgroup.
for (column = thread_index; column < width; column += 256) The universal loop: 256 threads each stride through the row, 256 elements apart.

7.5 · Stage 2: the ABI — the contract between C++ and Metal

Kernels receive their parameters as one plain struct. That struct must have the exact same layout on both sides of the GPU boundary, so it is written once and included by both the C++ dispatcher and the .metal file. Example — models/qwen4exp/abi/HyperConnection.h (whole file): 

#pragma once
// Parameter layouts shared by host dispatch code and Metal kernels.
#ifdef __METAL_VERSION__
#include <metal_stdlib>
#else
#include <stdint.h>
#endif

struct HyperConnectionParams {
  uint32_t rows;
  uint32_t hidden;
  uint32_t count;
  uint32_t low_rank;
  float epsilon;
  uint32_t with_inject;   // 1 = also compute injection gates
  uint32_t row_step;      // logical row r lives at physical row r * row_step
  uint32_t splits;        // 0 or 1 = no split
};

static_assert(sizeof(HyperConnectionParams) == 32,
              "HyperConnectionParams must be 32 bytes on both sides");
  • #ifdef __METAL_VERSION__ — the same file compiles under both the C++ toolchain and the Metal compiler.
  • static_assert(sizeof(...) == 32) — if the layouts ever drift, the build fails. This is the whole safety mechanism.
  • Only plain data (uint32_t, float) — the dispatcher memcpys the struct straight into the command stream (see 5.8).

7.9 · Walkthrough of a real kernel: mtp_pick.metal

Now you have the vocabulary. Let's read a kernel that does something non-trivial: find the 16 largest values among 248K logits — the draft head's "what do I guess?" step. The problem with the obvious approach: scanning 248K logits on the CPU means copying them out of the GPU, which is slow. The kernel's trick: 64 threadgroups each keep only their 16 best candidates; the host merges 64 × 16 = 1024 candidates in a few microseconds. The file header says exactly this (mtp_pick.metal:6-9).

The signature (mtp_pick.metal:15-23):

kernel void mtp_pick_slices(device const bfloat *logits [[buffer(0)]],
                            device uint *ids     [[buffer(1)]],
                            device float *values [[buffer(2)]],
                            device float *mass   [[buffer(3)]],
                            constant uint &vocabulary [[buffer(4)]],
                            uint slice        [[threadgroup_position_in_grid]],
                            uint thread_index [[thread_index_in_threadgroup]],
                            uint simd_lane   [[thread_index_in_simdgroup]],
                            uint simd_group  [[simdgroup_index_in_threadgroup]]) {

Grid = 64 threadgroups; threadgroup s owns vocabulary slice s (3,880 logits each — 248,320 vocabulary ÷ 64 slices, Qwen4Exp.hpp:43). Output: per slice, the 16 largest (ids + values) plus the slice's max and softmax mass — enough for the host to compute the exact top token and its probability.

Phase 1 — max and mass (mtp_pick.metal:30-53):

threadgroup float staged[kPickSliceMax];        // scratch: my slice, in shared memory
float local_max = -INFINITY;
for (uint i = thread_index; i < count; i += kPickThreads) {
  const float v = float(logits[first + i]);
  staged[i] = v;                                 // park it in scratch
  local_max = max(local_max, v);
}
local_max = simd_max(local_max);                 // reduce across my 32 lanes
if (simd_lane == 0) best_value[simd_group] = local_max;   // lane 0 of each simdgroup writes scratch
threadgroup_barrier(mem_flags::mem_threadgroup); // all 8 simdgroups done writing?
// thread 0 reads the 8 per-simdgroup maxima → slice max m; second pass computes
// sum += exp(staged[i] - m) the same way → mass[2*slice] = m, mass[2*slice+1] = total

Every pattern from Figure 7 appears here: strided loop → simd_max → lane 0 writes threadgroup scratch → threadgroup_barrier → thread 0 combines the 8 simdgroups.

Phase 2 — sixteen rounds of argmax (mtp_pick.metal:54-82):

// Sixteen rounds of (value, lowest index) argmax, removing each winner.
for (uint round = 0; round < kPickCandidates; ++round) {
  // strided scan for (max value, lowest index) across my slice...
  for (uint i = thread_index; i < count; i += kPickThreads)
    if (staged[i] > v) { v = staged[i]; index = i; }
  // ...then a 32-lane tournament:
  for (uint offset = 16; offset > 0; offset /= 2) {
    const float other_v = simd_shuffle_down(v, offset);
    const uint  other_i = simd_shuffle_down(index, offset);
    if (other_v > v || (other_v == v && other_i < index)) { v = other_v; index = other_i; }
  }
  // barrier; lane 0 of each simdgroup publishes; thread 0 picks the overall winner:
  ids[slice * 16 + round] = bi == 0xFFFFFFFFu ? 0xFFFFFFFFu : first + bi;  // sentinel when a slice is short
  values[slice * 16 + round] = bv;
  if (bi != 0xFFFFFFFFu) staged[bi] = -INFINITY;   // erase the winner → next round finds the next max
  threadgroup_barrier(mem_flags::mem_threadgroup);
}

Note the trick in the last line: there is no "remove element" in shared memory — the winner is just erased by setting it to −∞, so the next round's argmax finds the next-largest. Ties break toward the lower token id (determinism — the engine's output must be reproducible).

And the C++ half of the contract (Qwen4ExpTarget.cpp:2530-2560) reads the 1024 candidates back, merges them into the top 16, and computes the exact confidence from each slice's (max, sum-of-exp) pair — no second GPU pass needed.

7.10 · The ops layer: how shared kernels get launched

Model code never names shared kernels directly. It calls an op, e.g. operators.linear().addDecodeBatch(graph, input, weights, output, ...), and the op chooses the right variant. Look at runtime/ops/Linear.cpp:

  • Variant selection — the LinearPlan constructor (~line 124) maps (phase, rows, epilogue, tile) to a pipeline name like "decode_linear_q4_n128_m24" or "prefill_linear_q4_n256_up_silu_sums". Dozens of hand-tuned variants live in runtime/metal/kernels/{prefill,decode}/linear_q4.metal.
  • Grid sizing — decodeGroups() (~line 236) computes how many threadgroups to launch so the GPU cores stay balanced; the thresholds are measured on Apple9/Apple10 GPUs, as the comments say.
  • Validation — validate() rejects workloads the kernels cannot express (e.g. sizes not divisible by the quantization group), loudly, at plan time.

That is the pattern for any shared kernel family: the .metal file has the variants; the op has the policy; the model folder just asks.

8.1 · Q4 matmul: one tile engine, twenty variants

Every 4-bit projection in the model runs through one tile engine, runtime/metal/kernels/common/q4_mpp_tiles.h (349 lines). A threadgroup computes an 8-row × TileN block of the output with one Metal tensor op per 64-column quant group: matmul2d_descriptor(8, TileN, 64) with execution_simdgroups<8>. The 4-bit weights are read as a typed tensor view — one aligned read of a 64×TileN tile at (quant_group*StorageN + tile_offset)*64/2 (q4_mpp_tiles.h:149-155); weights are stored in blocks of StorageN = 256 output columns, with one bf16 scale+bias pair per weight row per 64-column group.

The epilogue is the part worth reading (q4_mpp_tiles.h:170-178): 

accum += partial * scale + input_sums[row] * bias;   // per row, per quant group

Dequantizing with a bias means adding bias × (sum of the group's inputs) — so the bias enters as one multiply by a precomputed row sum of the input, never by re-reading weights. Those input sums are staged into threadgroup memory one quad of quant groups at a time, double-buffered — sum_offset = ((quant_group >> 2) & 1)*32 + (quant_group & 3)*8 (:171-185) — and the template's Pipelined mode runs two groups' matmuls before both epilogues, “bit-identical” per the comment at :190-195. Grids are persistent: one threadgroup per (core, wave), each walking output tiles with tile += persistent_groups, with a trailing threadgroup_barrier so the next tile's prologue cannot overwrite input sums the current epilogue still reads (comment at :230-238).

8.2 · MoE: routing, bucketing, tiles

runtime/metal/kernels/shared/moe.metal turns “10 of 512 experts per token” into grouped GPU work:

  • moe_route_select_q8 (_n512 for this model): top-10 experts + weights from Q8 router scores. Its K-slices are summed in fixed order and ties break to the lower expert id, so the host mirror topExperts (models/qwen4exp/Qwen4ExpTarget.cpp:419) reproduces the GPU's choice bit-for-bit — required, because the host must stage from SSD exactly the experts the GPU picked (section 5.1).
  • moe_group_routes (_512): buckets token ids by selected expert and produces the tile descriptors — (which expert, which token rows) — that the tile kernels consume.
  • moe_gather_rows: copies selected rows so each expert tile sees a dense block.
  • moe_expert_gate_up_q4_* / moe_expert_down_q4_* (m8/m32, n128/n256, _up_silu): the very same Q4 tile engine of section 8.1, pointed at per-expert weights by the descriptors. The _range variants take an expert-range view — the kernels behind wave staging (MoE::addExpertTilesInRange).
  • moe_combine (_no_residual): weighted sum of the experts' outputs back into the token stream.

8.3 · Attention: split-KV over a paged 8-bit cache

The KV cache is paged in 32-token pages (abi/ExecutionGeometry.h:16) quantized to 8 bits; verify rows are padded to 8 (abi/ExecutionGeometry.h:7). The shared tile header states the parallel contract (runtime/metal/kernels/common/q8_attention_tile.h:15-19): 

// A threadgroup owns one KV head, query tile and history split …
// GQA group as M = rows x query heads per KV head. Each split writes fp32
// partials and statistics for a fixed-order reduce. Prefill and verify
// share this device-operand page loop.

So the grid is (KV head × query tile × history-split): long contexts get parallelism by cutting the history into splits, each writing fp32 partials plus its (max, sum) statistics; a paired _reduce kernel combines them in fixed order, which is what makes split-KV bit-reproducible. Inside the tile, the running row-max rescale uses threadgroup atomics (q8_attention_tile.h:84). The variants — verify_attention_q8_split, _split_cooperative_scale, _split_kv2_g8, _split_kv2_g12 and their matching _reduces (decode/attention_q8.metal:142-150, 185+) — trade heads-per-threadgroup and page-quantization groups against context length; prefill has mirrored kernels over the same page loop.

8.4 · GDN: three phases, one barrier

The gated-delta-net layers carry a recurrent state per token stream. Decode runs all three phases — prologue (4-tap causal conv + SiLU, then q/k RMSNorm, common/gdn_primitives.h:5-21), the scan (128 state rows spread over 8 simdgroups), and the gate — inside one kernel launch for a batch of four requests (decode/gdn.metal: verify_gdn_fused/_vh32, verify_gdn_commit/_vh32, lanes current0..3/next0..3). The phases are separated by a device-side grid barrier, grid_completion (decode/gdn.metal:9-20): an atomic arrival counter, and the last thread to arrive resets it and bumps a generation counter so the barrier is reusable. Prefill keeps three separate kernels (prefill_gdn_prepare/scan/gate) — with many tokens per request, launch overhead amortizes away.

8.5 · Sampling: top-K without materializing softmax

The same shard-and-merge pattern as mtp_pick_slices (section 7.9) runs the sampler. Sorted-insert into a fixed top-K list with ties to the lower id (top_insert, decode/sampling.metal:4-19), 8 sorted per-simdgroup lists merged by top_shard_store, and per-slice (max, sum-of-exp) so the host gets exact probabilities. decode_sample_top32_sharded(_batch) and the _probs variants fill the top-32 buffer from section 4; decode_sample_sparse_draw samples from it; decode_sample_argmax_sharded + _reduce is greedy; decode_accept_dflash compares draft guesses against the target's top-1 and counts accepted tokens (runtime/ops/Sampling.cpp:191); verify_input_tokens commits the accepted run (Sampling.cpp:208).

8.6 · The model's own kernels

  • hyper_connection.metal — the residual-mixing layers. Header states the math: streams are one row of Count×Hidden each; xn = rms_per_stream(x)*(1+gain); w = silu(down(xn)/Count); w = sigmoid(up(w)); input = mean over streams of reshape(w)*reshape(xn); injections scaled by 2*sigmoid(block_inject(xn)/Count).
  • qsa_indexer.metal — scores for the sparse-attention block selection: visible keys are compressed into CompressRatio-token blocks (fp32 mean, then rms*(1+k_gain) and RoPE); a block's score is Σ relu(dot(q, rotated_key))/√D over query rows.
  • qsa_select.metal — keeps 512 blocks (512 × 128 tokens = 65,536 context) by k-th-largest score. Scores are non-negative, so their IEEE bit patterns sort exactly like the values — a binary search over bit patterns finds the 512th largest, ties broken by block index ascending. No sort, no atomics.
  • mtp_pick_slices — section 7.9's walkthrough; per_layer_embedding / ngram_embedding — the embedding lookups of section 5; capture.metal — the capture path of section 4.

8.7 · One rule runs through every family: fixed order. Router K-slices summed in a stated order; ties to the lower id in routing, sampling, and block selection; k-th-largest by bit pattern; split-KV partials reduced in fixed order. The same GPU inputs produce the same token stream, which is what lets the tests in section 7.11 — and the porting playbook's token-for-token comparison — mean anything.

Known limit (stated honestly in the docs)

The shared runtime assumes the Qwen hybrid family: linear-attention (GDN) and full-attention layers, an 8-bit paged KV cache, and one recurrent state per request. A model from this family plugs in as above. A model outside it (e.g. pure attention with a different cache) also needs the runtime's buffers and state generalized — that work is not done (docs/architecture.md, "Honest limit").
